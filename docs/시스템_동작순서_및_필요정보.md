# ROS2 HIL 시스템 동작 순서와 필요 정보

## 1 목적

이 문서는 `ref/ROS2_HIL_담당자별_역할실행계획서.docx`를 기준으로 시스템의 실행 순서, 주행 중 동작, 개발 전에 정해야 할 정보를 정리한 문서다.

전체 시스템은 Vision과 Safety가 주변 상황을 감지하고, Decision이 최종 명령을 결정하며, Vehicle이 Gazebo 차량을 움직이는 구조다.

```text
Camera → Vision Node ───────────────┐
                                    │
초음파 → STM32 → Safety Bridge ────┼→ Decision Node → Vehicle Node → Gazebo 차량
                                    │        ↑                │
                                    └────────┴─ 차량 상태 ────┘
```

## 2 구성 요소별 역할

| 담당 | 구성 요소 | 역할 |
|---|---|---|
| A | Gazebo, Vehicle Node | `/cmd_vel`을 받아 차량을 움직이고 차량 상태와 위치를 발행한다. |
| B | Camera, Vision Node | STOP, GO, NONE 표지를 인식하고 결과와 인식 장애를 발행한다. |
| C | Ultrasonic, STM32, Safety Bridge | 장애물 거리를 판단해 CLEAR, WARNING, EMERGENCY, FAULT를 발행한다. |
| D | Decision Node, Docker | 모든 상태를 종합해 주행·정지 명령을 결정하고 전체 실행 환경을 관리한다. |

## 3 시스템 실행 순서

### 3.1 실행 준비

1. 모든 장비를 같은 네트워크에 연결한다.
2. 모든 장비의 `ROS_DOMAIN_ID`, `ROS_LOCALHOST_ONLY`, `RMW_IMPLEMENTATION`을 동일하게 맞춘다.
3. Vehicle PC에서 Gazebo GUI용 X11 환경을 확인한다.
4. Vision 장비에서 Camera 장치와 권한을 확인한다.
5. Safety 장비에서 STM32 Serial 장치와 권한을 확인한다.
6. 담당자별 Docker Compose 환경을 실행한다.
7. 컨테이너 안에서 ROS2 패키지를 빌드하고 환경을 적용한다.

```bash
docker compose -f docker-compose.yml -f docker-compose.<role>.yml up -d --build
docker exec -it ros2_hil_env bash
colcon build
source install/setup.bash
```

### 3.2 권장 노드 실행 순서

1. **Gazebo와 Vehicle Node 실행**
   - World와 차량을 생성한다.
   - `/cmd_vel` 구독과 차량 상태 발행을 확인한다.
2. **STM32와 Safety Bridge 실행**
   - STM32가 초음파 거리를 측정한다.
   - Safety Bridge가 UART 값을 `/safety/state`로 변환한다.
3. **Vision Node 실행**
   - Camera 또는 녹화 영상을 연다.
   - `/vision/sign`, `/vision/fault` 발행을 확인한다.
4. **Decision Node 실행**
   - Vision, Safety, Vehicle 상태를 구독한다.
   - 모든 필수 입력이 정상일 때만 주행을 허용한다.
5. **전체 연결 확인**
   - 정상 주행, STOP, GO, Emergency, Recovery, Fault 순서로 시험한다.

```bash
ros2 node list
ros2 topic list
ros2 topic info -v /cmd_vel
ros2 topic echo /vehicle/state
```

실제 안전성은 실행 순서에 의존하면 안 된다. 필수 Node가 늦게 실행되거나 중단되어도 Decision과 Vehicle은 Timeout을 감지해 차량을 정지해야 한다.

## 4 주행 중 동작 순서

### 4.1 정상 주행

1. Safety가 `CLEAR`를 발행한다.
2. Vision이 `NONE` 또는 `GO`를 발행한다.
3. Decision이 모든 입력과 Timeout을 확인한다.
4. Decision이 `DRIVING` 상태로 전환하고 `/cmd_vel`을 발행한다.
5. Vehicle Node가 명령을 Gazebo에 전달한다.
6. Gazebo 차량이 이동한다.
7. Vehicle Node가 `/vehicle/state`와 `/vehicle/pose`를 발행한다.

### 4.2 STOP 표지

1. Camera가 STOP 표지를 촬영한다.
2. Vision이 `/vision/sign = STOP`을 발행한다.
3. Decision이 `STOPPING`으로 전환한다.
4. Decision이 속도 0의 `/cmd_vel`을 발행한다.
5. Vehicle이 정지하고 `/vehicle/state = STOPPED`를 발행한다.
6. Decision은 GO 또는 재출발 조건이 들어올 때까지 정지를 유지한다.

### 4.3 GO 표지

1. Vision이 `/vision/sign = GO`를 발행한다.
2. Decision이 Safety `CLEAR`와 Fault 없음 여부를 확인한다.
3. 모든 조건이 정상이면 `DRIVING`으로 전환한다.
4. Decision이 주행 `/cmd_vel`을 다시 발행한다.

### 4.4 장애물 긴급 정지

1. 초음파 센서가 임계거리 이하의 장애물을 감지한다.
2. STM32가 `EMERGENCY`를 판정하고 UART로 전송한다.
3. Safety Bridge가 `/safety/state = EMERGENCY`를 발행한다.
4. Decision은 Vision 결과와 관계없이 즉시 정지 명령을 발행한다.
5. Vehicle과 Gazebo가 차량을 정지한다.
6. Decision은 차량의 `STOPPED` 상태를 확인한다.

### 4.5 장애물 제거와 복구

1. STM32가 일정 시간 안전 거리를 확인한다.
2. Safety가 `CLEAR`를 발행한다.
3. Decision이 `RECOVERY` 상태로 전환한다.
4. Vision, Safety, Vehicle, 통신 상태를 다시 확인한다.
5. 복귀 조건을 만족하면 주행하고, 만족하지 않으면 정지를 유지한다.

### 4.6 Fault 또는 통신 단절

1. Camera, 센서, UART, ROS2 Topic 중 하나에서 오류나 Timeout이 발생한다.
2. Decision이 `FAIL_SAFE` 상태로 전환한다.
3. 속도 0의 `/cmd_vel`을 발행한다.
4. `/system/fault`에 오류 상태를 발행한다.
5. 오류가 해제되어도 복구 조건을 확인하기 전에는 주행하지 않는다.

## 5 판단 우선순위

Decision은 다음 우선순위로 동작해야 한다.

```text
통신 또는 시스템 FAULT
  > Safety EMERGENCY
  > Safety WARNING
  > Vision STOP
  > Vision GO 또는 NONE
```

따라서 Vision이 GO를 보내더라도 Safety가 EMERGENCY이면 차량은 정지 상태를 유지한다.

## 6 사용 Topic

| Topic | 발행 | 구독 | 의미 |
|---|---|---|---|
| `/cmd_vel` | Decision | Vehicle | 차량 선속도와 각속도 명령 |
| `/vehicle/state` | Vehicle | Decision | STOPPED, DRIVING 등 차량 상태 |
| `/vehicle/pose` | Vehicle | Decision, RViz | 차량 위치와 방향 |
| `/vision/sign` | Vision | Decision | STOP, GO, NONE |
| `/vision/fault` | Vision | Decision | Camera 또는 인식 장애 |
| `/safety/state` | Safety Bridge | Decision | CLEAR, WARNING, EMERGENCY, FAULT |
| `/system/fault` | Decision | 전체 | 시스템 Fail-Safe 상태 |

## 7 개발 전에 반드시 필요한 정보

### 7.1 공통 환경

- Ubuntu와 ROS2 배포판
- Gazebo 버전
- 담당별 실행 장비와 Node 배치
- ROS Domain ID와 DDS 설정
- 장비 연결 방식과 방화벽 설정

### 7.2 ROS2 Topic 계약

각 Topic에 대해 메시지 타입, 허용 값, 단위, 발행 주기, QoS, Timeout과 오류 처리 방법을 확정해야 한다.

| Topic | 초기 메시지 타입 제안 | 추가 결정 사항 |
|---|---|---|
| `/cmd_vel` | `geometry_msgs/msg/Twist` | 최대 속도, 발행 주기, Timeout |
| `/vehicle/state` | `std_msgs/msg/String` | 허용 상태와 정지 판단 기준 |
| `/vehicle/pose` | `geometry_msgs/msg/Pose2D` | 좌표계, 발행 주기, TF 사용 여부 |
| `/vision/sign` | `std_msgs/msg/String` | 인식 확정 횟수와 반복 발행 조건 |
| `/vision/fault` | `std_msgs/msg/Bool` 또는 Custom | Fault 원인과 해제 조건 |
| `/safety/state` | `std_msgs/msg/String` | 상태별 거리와 전환 조건 |
| `/system/fault` | `std_msgs/msg/String` 또는 Custom | 원인, 심각도, 복구 여부 |

### 7.3 Vehicle과 Gazebo

- 차량 크기, 질량, 바퀴 반지름과 간격
- 최대 속도, 가속도와 감속도
- 명령 단절 후 정지할 Timeout
- 차량을 STOPPED로 판단할 속도 기준
- 차량 Spawn 위치와 World 좌표계
- `/odom`, TF, `/vehicle/pose` 발행 방식

### 7.4 Vision

- Raspberry Pi와 Camera 모델, 장치 경로, 해상도와 FPS
- ArUco 또는 QR 사용 여부
- STOP과 GO Marker ID와 크기
- 인식 거리와 최소 신뢰도
- 몇 Frame 연속 인식해야 확정할지
- Camera 단절과 인식 실패의 Fault 기준

### 7.5 STM32와 Safety

- STM32 Board와 초음파 센서 모델
- 센서 측정 주기와 필터 방식
- WARNING과 EMERGENCY 거리
- 장애물 제거 후 CLEAR 판정 시간
- UART Baud Rate와 Packet 형식
- 센서 무응답과 UART 단절의 Fault 기준

### 7.6 Decision 정책

- 시스템 최초 상태와 주행 시작 조건
- FSM 상태별 진입·해제 조건
- STOP 후 대기 시간과 GO 처리 방식
- WARNING 시 감속 속도
- Emergency 해제 후 자동 또는 수동 재출발 여부
- Vision Fault 발생 시 감속 또는 정지 여부
- 각 입력 Topic의 Timeout과 동시 이벤트 우선순위

## 8 가장 먼저 결정할 항목

1. Topic별 메시지 타입, 값, QoS와 Timeout
2. Decision FSM 상태 전이와 판단 우선순위
3. Safety WARNING·EMERGENCY 거리와 Recovery 조건
4. Vision Marker 종류, ID와 인식 확정 조건
5. `/cmd_vel` 속도, 발행 주기와 Vehicle Timeout
6. UART Packet 구조와 통신 장애 기준
7. 통합 시험의 성공 조건

## 9 현재 저장소에서 추가로 필요한 구현

| 구성 | 현재 상태 | 필요한 작업 |
|---|---|---|
| Vehicle Node | `/cmd_vel`을 `/vehicle/control_cmd`로 전달 | Timeout, 명령 검증, 차량 상태와 위치 발행 |
| 수동 명령 GUI | FRONT와 STOP을 `/cmd_vel`에 발행 | 통합 시 Decision과 동시 실행되지 않도록 제어 |
| Gazebo | World와 Launch 존재 | 차량 Model Spawn과 제어 Plugin 연결 확인 |
| Decision Node | 패키지 골격만 존재 | 입력 구독, FSM, 주행 명령, Fault 처리 구현 |
| Vision Node | 없음 | Camera 입력, 표지 인식, Sign과 Fault 발행 구현 |
| Safety Bridge | 없음 | UART 수신, 상태 변환, Timeout 구현 |
| STM32 Firmware | 없음 | FreeRTOS Task, 거리 판단, UART 전송 구현 |

## 10 권장 개발 순서

1. Topic, UART, FSM 명세를 확정한다.
2. A, B, C, D가 각각 Fake 데이터로 독립 실행한다.
3. Decision과 Vehicle을 연결한다.
4. Vision과 Decision을 연결한다.
5. Safety Bridge와 Decision을 연결한다.
6. 실제 Camera와 STM32를 연결한다.
7. 정상, STOP, GO, Emergency, Recovery, Fault를 순서대로 검증한다.
8. 새 환경에서 Clean Build와 전체 재실행을 확인한다.

완료 기준은 모든 시나리오가 반복 실행해도 같은 결과를 내고, 로그 또는 Rosbag으로 입력부터 차량 반응까지 확인할 수 있는 상태다.
